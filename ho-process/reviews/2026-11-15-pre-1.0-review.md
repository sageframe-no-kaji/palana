# Pre-1.0 Review — 2026-11-15

Scope: `56e6445..97b630c` (40 commits). Earlier findings are in `2026-09-06-full-code-review.md`.

## Ruling

The review found 3 release-blockers, 6 should-fix defects, and 8 notes.

Two release-blockers lose data through the new progressive rsync move (`def967f`). In both cases the move reports success after deleting the source. The third blocker comes from the 09-08 auto-refresh: the app leaks one file descriptor and one dispatch source on every local navigation. After a few hundred navigations in one session, a Finder-launched copy runs out of descriptors.

All three are cheap to fix. Each needs a test that reproduces the failure before the fix lands.

## Findings

### 1. Release-blocker — a move into the directory it already occupies deletes the selection and reports success

- WHERE: `Sources/PalanaCore/Plan/PlanEngine.swift:171-175` (a `.merge` collision forces `.crossDatasetCopyPlusDelete`), `Sources/PalanaCore/Plan/PlanEngine.swift:313-316`, `Sources/PalanaCore/Plan/PlanEngine+Rsync.swift:70-77` (openrsync accepted for source removal), `Sources/Palana/OperationModel.swift:206-228` (no same-place guard; only drag-and-drop has one, at `DraggedSelection.swift:81`).
- SCENARIO: Both panes show `local:/Users/example/Projects`, and the Mac has only the system rsync (openrsync). The operator selects folder `a`, optionally with files beside it, and presses `m`.
  1. The collision gather lists the destination, which is the same directory. `a` collides with itself, so the nature is `.merge`.
  2. `classify` routes every merge to copy-plus-delete, and `carriesSourceRemoval` accepts openrsync.
  3. The plan reads "will merge into a" and runs `rsync -a --partial --checksum --remove-source-files /…/a /…/f /…/`.
  4. Every file is "already up to date" against itself, so rsync removes it.
  5. The sweep `rmdir`s the emptied tree, and the leftover report finds nothing.

  Reproduced with openrsync: rsync exit 0, report exit 0, and the directory is gone. The same happens through an aliased path: a symlinked or bind-mounted directory, or `/srv/x` vs `/mnt/pool/x`. That route is reachable even with distinct pane paths.

  rsync 3.4.1 refused with `Skipping sender remove of destination file` (exit 23, nothing lost). Its NEWS dates that safety check to 3.2.6, and it covers local copies only. Remote hosts are exposed when they carry openrsync or rsync 3.0–3.2.5, such as Debian 11 and Ubuntu 20.04. Also exposed: the same machine reached through two SSH aliases (cross-host route). I have not verified whether 3.2.6+ catches that case.
- FIX:
  - Refuse any move or copy whose source and destination resolve to the same directory. Use `cd -P && pwd -P` on the host, not a lexical comparison.
  - Prefix each progressive transfer with a guard step that refuses when the source entry and its destination target are the same file: `[ "$src" -ef "$dst/$name" ]`, applied per entry.
  - Consider requiring rsync ≥ 3.2.6 (or the `-ef` guard) for source removal, and keeping openrsync to copies.
  - Add a live LocalConduit test that moves a folder into its own directory with `/usr/bin/rsync`.

### 2. Release-blocker — operator rsync flags defeat the move's content check; the source is deleted after a wrong or missing landing

- WHERE: `Sources/PalanaCore/Plan/PlanEngine+Rsync.swift:37-42` (operator flags spliced into a move), `:104-112` (only `remove-source` / `remove-sent` are reserved).
- SCENARIO: The engine appends `--checksum --remove-source-files` after the operator's flags, so an operator `--no-checksum` is overridden. Additive flags are not, and each of these was reproduced with the engine's exact command sequence:
  - `--append` (a plausible "resume big transfers" setting), on a merge where `dst/dir/f` = `OLD\n` and `src/dir/f` = `SOURCE-CONTENT-…`. rsync 3.4.1 exits 0. The destination becomes `OLD\nCE-CONTENT-…` (corrupted), the source is removed, and the report succeeds. The original bytes exist nowhere.
  - `--compare-dest=DIR`: files matching in `DIR` are never written to the destination but are removed from the source. The run reports success with those files missing from the destination (rsync 3.4.1 and openrsync).
  - `-m` / `--prune-empty-dirs`, or an `--exclude` that hits a directory: empty source directories are not created at the destination but are swept. The run reports success.
  - `-n` / `--dry-run`: nothing transfers, but the sweep still deletes empty source directories before the report fails.
- FIX:
  - For moves, ignore operator flags or apply an allow-list (`--bwlimit`, `-z`/`--compress`, `-v`, `--info=…`, `--stats`).
  - Refuse any plan whose move carries other flags.
  - Run the sweep only when the transfer was a real (non-dry-run) transfer.
  - Defense in depth: verify the landed bytes for each entry before release. The manifest code (finding 16) is already written.

### 3. Release-blocker — every local navigation leaks the pane watcher's descriptor and dispatch source

- WHERE: `Sources/Palana/PaneModel+Refresh.swift:74-82` (`cancel()` hops to the queue with `[weak self]`), `:184-199` (`keepCurrent` drops the old watcher immediately after `cancel()`), `:143-148` (`cancelAll`), `Sources/Palana/PaneModel.swift:190-192`, `:464`.
- SCENARIO:
  1. `refresher.watcher?.cancel()` queues an async block that weakly captures the watcher.
  2. The next line, `refresher.watcher = watcher`, releases the last strong reference, so the watcher deinitialises first.
  3. When the queued block runs, `self` is nil, so the source is never cancelled. Its cancel handler, the only `close(descriptor)`, never runs.

  A standalone copy of this pattern, after 50 re-points, showed open descriptors going from 4 to 54 with 0 cancel handlers run. Every loud local read (navigation, refresh, ⌘1–⌘9, history) and every pane retirement leaks one `O_EVTONLY` descriptor plus an armed source.

  A Finder-launched app has a soft limit of 256. A few hundred local navigations in one session exhaust it. After that, `open()` in later watchers fails silently, and every `Process`/ssh spawn and pipe fails with `EMFILE`, so transfers and listings stop working. The leaked `O_EVTONLY` handles also keep visited directories busy, which can block ejecting an external volume that was browsed.

  The tests miss it because `PaneRefreshTests.swift:128,151,171` hold `old`/`watcher` strongly while waiting for the count to drop.

  The same `queue.async { [weak self] … }` cancel exists in `RoundTripWatcher.cancel()` (`Sources/PalanaCore/Surface/RoundTrip.swift:310-320`). It is outside this range; check whether its records are released right after cancel.
- FIX:
  - Capture `self` strongly in `cancel()` (`queue.async { self … }`), or cancel the source synchronously (`queue.sync`).
  - Add `deinit { source?.cancel() }` as a backstop. A resumed source must be cancelled before release.
  - Change the tests to drop their reference before asserting closure: measure open descriptors through `/dev/fd`, or expose a static live-descriptor counter.

### 4. Should-fix — progressive moves strip extended attributes, Finder tags, resource forks, and ACLs, then delete the originals

- WHERE: `Sources/PalanaCore/Plan/PlanEngine+Rsync.swift:33-36` (`-a` only; no `-X`/`-A`, and nothing equivalent for openrsync).
- SCENARIO: A file on the Mac carries `com.example.note` and a Finder tag (`com.apple.metadata:_kMDItemUserTags`) and is moved to another volume. Both rsyncs exited 0, the source was gone, and the destination kept only `com.apple.provenance`. The same applies to POSIX ACLs and Samba/NAS xattrs on Linux hosts, and to ownership whenever the move runs as non-root (`-o`/`-g` silently no-op). A cross-volume `mv` preserved these on macOS before moves were refused, so this is a regression from the user's point of view.
- FIX:
  - Add `-X` (and `-A` where both ends support it) for source-removing routes, and probe support.
  - On the Mac's local cross-volume route, consider `ditto` or `cp -pR` plus explicit release.
  - Otherwise, name the metadata loss in the plan's warning line.

### 5. Should-fix — the reserved-flag check is a substring test that openrsync abbreviations bypass

- WHERE: `Sources/PalanaCore/Plan/PlanEngine+Rsync.swift:104-112`, `Sources/PalanaCore/Transports/Transports+ProgressiveMove.swift:7-10`.
- SCENARIO: openrsync parses long options with getopt_long, which accepts unambiguous prefixes. Reproduced: `/usr/bin/rsync -a --rem src/f dst/` (and `--remove`, `--remove-s`, `--remove-sou`) exits 0 and deletes `src/f`. rsync 3.4.1 rejects the abbreviations.
  1. An operator flag string containing `--rem` passes `validateRsyncOperatorFlags` and the enactment check.
  2. A copy plan then deletes its sources, with no `--checksum` and no leftover accounting, under a plan that says "copy".
  3. Quoted spellings (`--remove-'source'-files`) bypass the check on every rsync, because the string goes through a shell.
- FIX: Use the same allow-list as finding 2, tokenising the flags with the shell's rules. At minimum, reject any token that is a prefix of `--remove-source-files` or `--remove-sent-files` of length ≥ 4, and reject quotes and backslashes in operator flags.

### 6. Should-fix — enactment refuses legitimate plans whose paths contain "remove-sent" or "remove-source"

- WHERE: `Sources/PalanaCore/Transports/Transports+ProgressiveMove.swift:7-14`, called first in `Transports.swift:104`.
- SCENARIO: The check lowercases every step's whole command, paths included. Copying an Outlook export named `Remove-Sent-Items.pst`, a folder `remove-source-later/`, a destination under such a directory, or a ZFS dataset with that substring fails before any step runs: `malformedPlan("source-removing rsync options belong only to a progressive move")`. A rename-route move of such a file fails the same way (`usesProgressiveRsyncMove` is false for `.withinDatasetRename`).
- FIX: Decide "removes source files" from the plan's structure (operation, transport, classification), not from command text. If a text check stays, inspect only the rsync flag tokens before the first path argument.

### 7. Should-fix — a failed transfer in a progressive move produces no retained-source accounting

- WHERE: `Sources/PalanaCore/Plan/PlanEngine.swift:354-371` (sweep and report are ordinary later steps), `Sources/PalanaCore/Transports/Transports.swift:70-80` (the first nonzero step ends the run).
- SCENARIO: The operator moves 300 files. Halfway through, one file is unreadable, or a file is modified during the move ("Skipping sender remove for changed file"). rsync exits 23 and the run stops. About half the sources are already deleted and half remain, but the report step never runs, so no `palana-retained:` notes appear. The operator gets rsync's last 4 KB of stderr and has no list of what is where. The README promises that pālana "reports anything left behind".
- FIX: Run the leftover report as a `finally`-style step after a failed transfer (not the sweep, which could delete directories that never landed). Alternatively, have Transports run the report step for `usesProgressiveRsyncMove` plans on any exit, including cancellation.

### 8. Should-fix — on a filesystem without hard links, every send-back moves the remote file aside, deletes the staged edit, and leaves the path empty

- WHERE: `Sources/PalanaCore/Plan/RemoteVersionGuard.swift:154-173`.
- SCENARIO: The remote destination is on exFAT/FAT, a CIFS mount without unix extensions, or an rclone/FUSE mount, any of which return EPERM/ENOTSUP for `link(2)`. The operator saves a round-trip edit.
  1. `mv -n entry kept` succeeds.
  2. `ln staged entry` fails, and the restore `ln kept entry` fails for the same reason.
  3. The program prints `palana-retained: … the destination was taken while the send was committing`, which is false. It then runs `rm -rf` on the staging directory, deleting the uploaded edit, and exits 7.

  The remote pathname is now empty; the original sits under `palana-replaced-<token>`. The edit survives only in the Mac's temporary copy. Every later save repeats this.

  Verified by reading. Not reproduced: no hard-link-less volume was mounted for this review.
- FIX: Restore with `mv -n -- kept entry` (rename needs no hard-link support), not `ln`. When the first `ln` fails, distinguish "exists" from "unsupported" (`[ -e entry ]`). On an unsupported filesystem, fall back to a no-clobber rename promotion, or refuse before setting the version aside. Keep the staged copy and name it in a retained note whenever the commit does not land.

### 9. Should-fix — reordering in the Global favorites group partitions by host

- WHERE: `Sources/PalanaCore/Surface/FavoritesList.swift:88-93,108-110` (group = same `scope` and same `host`), compared with `Sources/PalanaCore/Surface/FavoritesOutline.swift:159-168` (the Global group shows every `.global` favorite, whatever its host).
- SCENARIO: The Global group shows `[A (local), B (nas), C (local)]`.
  - Dragging A onto B is silently refused: B is "outside the group".
  - ⌥↓ on A moves it to the end of the local subset: the display becomes `[C, B, A]`, so A jumped past B and B can never be passed.
  - ⌥↑/⌥↓ on B does nothing.
  - Dropping on the lower half of the last row (`nextID == nil`) sends the favorite to the end of its host subset, not the end of the visible group.

  Each of these still pushes an undo snapshot (note 12). Numbering (⌘1–⌘9) follows the display, so the numbers visibly jump around the operator.
- FIX: Define the reorder group the way `FavoritesOutline.groups` does: all `.global` favorites form one group, and `.host` favorites group per host. Add a test with mixed-host globals.

### 10. Note — a move into the selection's own descendant goes progressive and nests the data

- WHERE: `Sources/Palana/OperationModel.swift:206-228`, `Sources/PalanaCore/Plan/PlanEngine.swift:109-129`.
- SCENARIO: The source pane shows `/d` with `a` selected, and the destination pane shows `/d/a/sub`. Reproduced with both rsyncs: everything ends at `/d/a/sub/a/{x,sub/y}`, the report flags `/d/a` as retained, and the run fails. No bytes are lost, but the tree is rearranged before the refusal.
- FIX: Refuse when any selected directory is the destination or an ancestor of it, using the same resolved-path check as finding 1.

### 11. Note — retained-source notes are lost once the report exceeds 4 KB

- WHERE: `Sources/PalanaCore/Transports/Transports.swift:335-356`, `Sources/PalanaCore/Transports/EnactmentEvent.swift:116-127`.
- SCENARIO: Notes are lifted from a 4,096-byte suffix of stderr. When many sources remain (for example 60 entries with long paths), the earliest lines fall out of the tail. If the cut lands inside a multi-byte character, `String(bytes:encoding:.utf8)` returns nil and the run gets no notes at all, with an empty `stderrTail` in the failure. Every retained line carries a 3-byte em dash, so the risk is real. The raw echo still shows the lines. A path containing a newline also splits its note.
- FIX: Parse notes from the full stderr stream line by line as chunks arrive, rather than from the truncated tail. Decode lossily.

### 12. Note — favorites moves push an undo step and persist even when nothing moved

- WHERE: `Sources/Palana/FavoritesModel.swift:91-102`.
- SCENARIO: ⌥↑ on the first favorite three times, then a refused cross-group drag, pushes four identical snapshots. The next four ⌘Z presses appear to do nothing.
- FIX: Snapshot and persist only when `list` actually changed (compare before and after).

### 13. Note — a failed send-back transfer leaves its staging directory behind, unannounced

- WHERE: `Sources/PalanaCore/Plan/PlanEngine+Binding.swift:76-84`.
- SCENARIO: The steps are `mkdir palana-send-<token>`, then the transfer, then the commit. If the transfer fails (connection drop, disk full), the run stops before the commit, which is the only step that cleans up. A `palana-send-<token>/` directory with a partial file stays in the user's remote directory with no `palana-retained:` note.
- FIX: On a transfer failure in a version-bound plan, run `rm -rf -- staging` as a cleanup step, or at least emit a retained note naming it.

### 14. Note — the local watcher does not see in-place changes to files

- WHERE: `Sources/Palana/PaneModel+Refresh.swift:101-104`.
- SCENARIO: The vnode source watches the directory. A file growing in place (a download, a log) does not write the directory, so the local pane keeps showing its old size and mtime until something else triggers a re-read. Remote panes poll and do not have this problem. The header comment says "anything in it changes".
- FIX: Document the limitation, or use FSEvents (`kFSEventStreamCreateFlagFileEvents`) for local panes.

### 15. Note — custom rsync flags bypass the overwrite and merge reporting on copies too

- WHERE: `Sources/PalanaCore/Plan/PlanEngine+Rsync.swift:37-39`.
- SCENARIO: `--delete` in operator flags turns a merge copy into a destination purge of entries not in the source. The plan's collision line still says "will merge into …". This predates the range, but the move route now exposes it too.
- FIX: Fold into the allow-list from finding 2.

### 16. Note — manifest verification is dead code

- WHERE: `Sources/PalanaCore/Transports/EnactmentEvent.swift:43,56-63`, `Sources/PalanaCore/Transports/Transports.swift:235-237`, `Sources/Palana/OperationModel+Descriptions.swift:11-14`.

### 17. Note — the release `.app` does not ship SwiftPM resource bundles

- WHERE: `scripts/build_macos.sh:68-80,100-105`.
- SCENARIO: SwiftTerm declares `.process("Apple/Metal/Shaders.metal")`, so the build emits `SwiftTerm_SwiftTerm.bundle`. The script copies only the executable. This is harmless today: `MetalTerminalRenderer` is the only `Bundle.module` user, and pālana never enables the Metal renderer. Enabling it would `fatalError` on users' machines. The per-arch build plus `lipo` merge itself looks correct, and `set -euo pipefail` is in force.
- FIX: Copy any `*.bundle` from the bin directory (one arch suffices for resources) into `Contents/Resources`, or leave a comment pinning the Metal-off assumption.

## Checked and found sound

- The engine's `--checksum` comes after operator flags and wins over `--no-checksum`/`--size-only`. Verified: with same size and mtime but different bytes, both rsyncs replaced the destination before removing the source.
- `--ignore-existing`, `--update`, `--existing`, and `--max-size` skip files without removing them, and the report catches the retained roots.
- Quoting of composed paths: `ShellQuote` everywhere, absolute paths (no leading-dash arguments), `-s` on every modern route, and inner quoting on the openrsync direct route. Non-UTF-8 names are refused at `validate` (`unrepresentableName`).
- The shell toggle policy (`ShellTogglePolicy`): no path dismisses a running operation, and the key monitor gates on `shellVisible && shellFocused`. The click monitor never starts a session.
- Remote poll: weak capture per tick, gates on activity, suspension, and in-flight reads. Quiet reads are superseded by loud ones through `loadTask.cancel()` and the post-await `isCancelled` check.
- `FavoritesList.move(id:by:)` index arithmetic and `FavoritesOutline.number(forChord:)` (`cmd-shift-8` does not parse as a number).
- `RemoteVersionGuard` on hard-link-capable filesystems: no-clobber set-aside, digest re-proof before deleting the displaced copy, and every refusal clears staging.
- `OperationLog`'s `SinkHolder`, the `RunningCommand.output()` termination stop, and `ToolReads` cancellation teardown.
